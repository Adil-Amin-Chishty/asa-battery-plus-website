# Deployment and operations

## Architecture

The browser loads the Next.js storefront and admin interface from Netlify. Next.js server routes connect to hosted Turso/libSQL using private environment variables. The database holds brands, products, WebP photo bytes, sessions, failed-login limits and catalog initialization settings. Photo background removal runs in a browser worker; the server normalizes the result before database storage.

Local development falls back to `storage/catalog.sqlite` only when no remote database URL is configured. A local `.env.local` containing Turso credentials connects development to that hosted database too: edits from such a development session affect the same live catalog. Use a separate development database when testing changes.

## Private environment variables

Configure these in **Netlify → Project configuration → Environment variables**, for production builds and functions. Do not prefix them with `NEXT_PUBLIC_` or put actual values in GitHub issues, README files, command arguments or screenshots.

| Variable | Purpose |
| --- | --- |
| `TURSO_DATABASE_URL` | Hosted libSQL endpoint |
| `TURSO_AUTH_TOKEN` | Database authorization token |
| `ADMIN_EMAIL` | Owner's sign-in identifier |
| `ADMIN_PASSWORD_HASH` | Complete salted scrypt hash generated by `npm run admin:setup` |
| `APP_ORIGIN` | `https://asa-battery-plus.netlify.app`, without a trailing slash |

Local private values belong in ignored `.env.local`. `.env.example` documents variable names with empty placeholders and is safe to commit. There is no default password. To reset the owner's login, run `npm run admin:setup` locally, update the corresponding private Netlify variables, and redeploy. Previous sessions become invalid after the configured credentials change.

## Redeploy source changes

1. Run the relevant checks locally. The repository's GitHub workflow builds and tests pushes to `main` and pull requests; this workflow does not itself publish to Netlify.
2. Commit and push source/configuration changes to GitHub.
3. Check **Netlify → Deploys** for a build of the new commit. The existing repository connection was configured with a manual provider at launch; do not assume every GitHub push triggers a deployment. If no build starts, use **Trigger deploy → Deploy site**. Configure Git-provider continuous deployment separately if automatic deploys are desired.
4. Confirm the deployment is **Published** and its commit matches the intended revision.
5. Open the public URL in a signed-out browser and verify actual routes. A “Ready” badge alone is insufficient.

Prefer Netlify's Linux cloud builds. Local Netlify CLI packaging on Windows failed at launch with `EPERM ... symlink` when the adapter copied dependencies. The same application built successfully on Netlify's Linux servers; enabling the correct runtime was also necessary.

Catalog edits through `/admin` do **not** need a redeploy. Source changes, environment changes and app icon/manifest changes do.

## Launch checks

- `/` displays the storefront and current public catalog.
- `/api/catalog` returns JSON with published products and visible brands.
- `/admin` displays the sign-in screen when signed out.
- `/api/admin/catalog` returns HTTP 401 when signed out.
- An existing `/api/media/<image-id>` URL returns the uploaded WebP image.
- `/admin/app.webmanifest` launches `/admin` in `standalone` mode; both referenced PNG icons load.
- The owner signs in, saves a deliberate catalog change and checks it on the storefront.
- The owner installs the admin on their own phone and checks the login/upload flow.

HTTP route, public catalog, uploaded image, manifest and icon checks were completed on 2 October 2026. Owner sign-in with a real password and physical-phone installation remain owner acceptance checks.

## Troubleshooting

| Symptom | Check / action |
| --- | --- |
| Netlify login screen or 401 on every page | Set production project visibility to Public. Keep the application's admin login enabled. |
| Build succeeds but every app route returns 404 | Set Runtime to Next.js in Netlify build settings, then redeploy. Check that a Next.js server handler appears in the deployment. |
| Catalog/API returns 500 | Check runtime logs and the Turso URL/token, database availability and free-tier allowance. Do not post raw credentials in a bug report. |
| Admin save/login returns “Request origin is not allowed” | Set `APP_ORIGIN` to the exact HTTPS origin used in the browser and redeploy. A custom domain needs its own origin value. |
| Admin access is not configured | Set both admin credential variables for functions and redeploy. |
| Uploaded photo is missing | Verify the deployment uses the database containing the photo bytes; uploads are not files committed to `public/`. |
| Photo cutout fails | Try a clearer image or Keep original. The worker requires a modern browser; model/runtime assets are prepared during build. |
| Site is paused | Review the Netlify and Turso usage dashboards. Free plans have limits; avoid unnecessary builds and check the provider's reset/recovery options. |
| Install menu is unavailable | Use Chrome on Android or Safari on iPhone, open `/admin` directly over HTTPS, and check the manifest/icons. Installation menus vary by browser. |

## Database transfer and backups

For an initial transfer from local SQLite to a new, empty hosted database, stop the local server, configure the destination Turso credentials privately, then run:

```sh
node scripts/migrate-catalog.mjs
```

The script transfers brands, products, photos and initialization settings in a transaction, excludes sessions/login attempts, verifies row counts and refuses to overwrite a different destination catalog. It leaves the source database unchanged. This is an initial migration tool, not a routine overwrite or backup command.

Back up hosted data through the database provider's export/backup facilities. Restore catalog records and photo bytes together. For local SQLite, use a SQLite-aware backup or copy the database while the app is stopped. Never commit a database backup containing private data to GitHub.

Docker Compose mounts `catalog_data` at `/app/storage`. This preserves the local database when no Turso URL is supplied; with Turso credentials configured, the app uses Turso instead. The Docker image excludes environment files, database files, local tool state and research material.

## What belongs in GitHub

Commit application source, dependency lockfile, build/deployment configuration, Docker files, static product assets, admin app icons/manifest, scripts, licenses and documentation.

Keep `.env.local` and other private environment files, database files/backups, access tokens, admin hashes, sessions, `.netlify/`, `.vercel/`, `.research/`, `.codex/`, `.agents/`, test output, generated image tools and build dependencies out of GitHub. `.gitignore` and `.dockerignore` handle these local exclusions. Live user uploads stay in the database. Public business details and the public website/admin URLs are intentional repository information.

If a secret is ever committed, revoke/rotate it at its provider; removing the latest file does not remove earlier Git history.
